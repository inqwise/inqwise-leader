== Purpose

`LeaderConsensus` provides lightweight leader coordination for Vert.x applications.
Instances in the same group coordinate through your existing Vert.x cluster and cluster manager,
so your application can start work when it becomes leader and stop starting work when leadership is lost.

The group name is the only required library-specific setting. Participants identify themselves automatically:
there are no predefined node IDs, peer lists or additional listener ports to configure.
No separate database, coordination service or persistent volume needs to be deployed for `LeaderConsensus`.
Use the default options to get started, and adjust timing when your application needs it.

== Use Cases

* Run a recurring maintenance or cleanup job on the current leader.
* Refresh shared caches or periodically synchronize external data.
* Select an instance to poll a service or coordinate background work.
* Run independent leader tasks by assigning each task a different group name.

== Simple Design

. Create a `LeaderConsensus` instance with a group name and your application's Vert.x instance.
. Instances with the same group name coordinate ownership through the cluster's shared data.
. The owner periodically confirms its leadership. Your callback receives `true` when leadership becomes ready
  and `false` when it is lost.
. Other instances can take over after ownership stops being confirmed. Restarted instances rejoin automatically,
  without recovering an identity or election files from disk.

For coordination across processes, all participants must belong to the same Vert.x cluster.
With a nonclustered `Vertx.vertx()`, coordination is limited to that one Vert.x instance.
Failure detection and partition behavior depend on your cluster manager and its configuration;
a network fault can leave the group without a ready leader until the cluster recovers.

== Quick Start

=== Add the dependency

Use Java 21+ and provide the Vert.x and Log4j runtime dependencies required by your application.
Add Inqwise-Leader to your Maven project, with `latest.version` set to the library version you want to use:

[source,xml]
----
<dependency>
  <groupId>com.inqwise</groupId>
  <artifactId>inqwise-leader</artifactId>
  <version>${latest.version}</version>
</dependency>
----

=== Run work while this instance is leader

Create the consensus instance inside your verticle's `start()` method so leadership callbacks
and job timers share its context. Register the callback before starting the election.

[source,java]
----
import com.inqwise.leader.LeaderConsensus;
import com.inqwise.leader.LeaderConsensusOptions;
import io.vertx.core.AbstractVerticle;

public class LeaderWorker extends AbstractVerticle {
    private LeaderConsensus consensus;
    private long jobTimer = -1;

    @Override
    public void start() {
        consensus = new LeaderConsensus(
            "scheduled-job", vertx, new LeaderConsensusOptions());

        consensus.onLeaderChange(isLeader -> {
            if (isLeader && jobTimer == -1) {
                jobTimer = vertx.setPeriodic(5000, timerId -> {
                    if (consensus.getIsLeader()) {
                        System.out.println("Running the scheduled job");
                    }
                });
            } else if (!isLeader) {
                stopJob();
            }
        });

        consensus.start();
    }

    private void stopJob() {
        if (jobTimer != -1) {
            vertx.cancelTimer(jobTimer);
            jobTimer = -1;
        }
    }

    @Override
    public void stop() {
        stopJob();
        if (consensus != null) {
            consensus.stop();
        }
    }
}
----

For a local trial, deploy the worker on a regular Vert.x instance:

[source,java]
----
import io.vertx.core.Vertx;

var vertx = Vertx.vertx();
vertx.deployVerticle(new LeaderWorker())
    .onFailure(Throwable::printStackTrace);
----

This local trial has one participant and no failover. For a local demonstration with competing participants,
deploy additional `LeaderWorker` instances on that same Vert.x instance.

Keep callbacks and job handlers nonblocking. `start()` begins participation asynchronously;
wait for the leadership callback before starting leader work.
Call `stop()` when undeploying the worker. Cancelling a timer prevents future ticks,
but it does not cancel an operation already in progress.

== Advanced Examples

=== Run across a cluster

Deploy the same worker on each participating process using the clustered Vert.x instance your application already creates.
Here, that instance is named `clusteredVertx`:

[source,java]
----
clusteredVertx.deployVerticle(new LeaderWorker())
    .onFailure(Throwable::printStackTrace);
----

Use the same group name, `scheduled-job`, in every process that should coordinate this job.
The library reuses the configured cluster manager; you do not need a separate node ID, seed list or election port.
An instance joining an active group does not displace a healthy owner.
See link:docs/cluster-election.adoc#_deployment_and_safety_boundaries[deployment and upgrade guidance]
for cluster-manager requirements and handover from the older election protocol.

=== Coordinate independent jobs

Use different names when jobs should have independent leaders:

[source,java]
----
var options = new LeaderConsensusOptions();
var cleanup = new LeaderConsensus("cleanup", vertx, options);
var refresh = new LeaderConsensus("cache-refresh", vertx, options);

cleanup.onLeaderChange(isLeader ->
    System.out.println("Cleanup leadership: " + isLeader));
refresh.onLeaderChange(isLeader ->
    System.out.println("Cache refresh leadership: " + isLeader));

cleanup.start();
refresh.start();
----

Each group elects independently, so one instance may lead both jobs or each job may have a different leader.
Give each group its own job handler, and stop both consensus instances when the owning verticle stops.

=== Adjust election timing

The defaults confirm ownership every 1000 ms and use a leadership timeout of at least 3000 ms.
For a longer timeout, build options explicitly:

[source,java]
----
var options = LeaderConsensusOptions.builder()
    .withPendingToLeaderMsgTime(6000L)
    .withLeaderCycleMsgTime(1000L)
    .build();

var consensus = new LeaderConsensus("scheduled-job", vertx, options);
----

`withPendingToLeaderMsgTime` sets the observation timeout; `withLeaderCycleMsgTime` sets the confirmation interval.
The effective timeout is at least three confirmation intervals.
Longer timeouts tolerate slower cluster responses but delay takeover after failure.

=== Read options from application configuration

The same options can come from a Vert.x configuration object:

[source,json]
----
{
  "pending_to_leader_msg_time": 6000,
  "leader_cycle_msg_time": 1000
}
----

Inside your verticle's `start()` method:

[source,java]
----
var options = new LeaderConsensusOptions(config());
var consensus = new LeaderConsensus("scheduled-job", vertx, options);
----

Omitted options use their defaults. Register your leadership handler and call `start()` as in the quick start.

=== LeaderCoordinator

If you need durable Raft coordination, explicit voting membership or leadership fencing tokens,
use the separate `LeaderCoordinator` API. It manages its own peer communication and persistent state,
with different setup and deployment requirements from `LeaderConsensus`.

See the link:docs/leader-coordinator.adoc[LeaderCoordinator usage guide] for single-node and multi-node examples,
joining nodes, discovery, lifecycle and restart behavior.

[[raft-certificates]]
For authenticated coordinator communication, see the
link:docs/leader-coordinator.adoc#raft-certificates[TLS example and certificate setup].
For external writes that must reject stale leaders, see link:docs/raft-fencing.adoc[application fencing].
